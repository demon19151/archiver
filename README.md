# Собственный архиватор

Учебный lossless-архиватор с HTTP API и демонстрационным сайтом. Реализация не вызывает ZIP/GZIP/Zstandard/LZMA: сжатие выполняется собственными LZSS и каноническим кодированием Хаффмана. Node.js используется только для HTTP, SHA-256 и файлового интерфейса.

Пользовательский сайт поддерживает пакетную обработку: можно выбрать или перетащить сразу несколько исходных файлов, архивировать их по одному и скачать всё одной кнопкой. При нескольких файлах они складываются в самостоятельный контейнер `SARB`; одиночный файл остаётся обычным `.sarc`. Для распаковки `.sarb` сайт извлекает записи и передаёт каждый `.sarc` в API. После распаковки одна кнопка скачивает ZIP-файл с каталогом `restored-files/` и всеми восстановленными файлами внутри. Arena API остаётся совместимым с протоколом: один POST-запрос обрабатывает один файл.

## Выбранная стратегия

При сжатии создаются несколько кандидатов и выбирается самый короткий вместе со служебными данными:

* **store** — исходные байты без обработки; обязательный безопасный fallback для случайных и уже сжатых файлов. В v4 накладные расходы — 5 байт;
* **RLE / repeat** — компактное кодирование серий одинаковых байтов и периодически повторяющихся блоков;
* **LZSS + Huffman** — универсальный режим: окно 64 КБ, совпадения до 258 байт, затем Huffman по потоку токенов;
* **Huffman** — полезен для файлов с сильно неравномерным распределением байтов;
* **delta + LZSS + Huffman** — пробуется для подходящих числовых данных;
* **stride-delta / byte-shuffle + LZSS + Huffman** — исследуются шаги 2, 4 и 4096 байт. Это может помочь PCM/WAV, числовым массивам, фиксированным бинарным записям и страницам SQLite.

LZSS использует ограниченный hash-chain поиск, который уменьшается на больших файлах. Быстрый отбор по небольшой выборке пропускает заведомо высокоэнтропийные данные, а RLE/repeat могут завершить выбор ранним результатом. Для маленьких файлов накладные расходы таблицы Хаффмана автоматически делают `store` лучшим кандидатом. Расширение и сигнатура файла не используются для выбора метода.

## Формат SARC v4

Новая версия использует код метода как первый байт, без общей сигнатуры, и 32-битную контрольную сумму SHA-256. Пустой файл имеет специальное однобайтовое представление `00`: нулевой размер невозможен, потому что распаковщик не сможет отличить отсутствующий запрос от корректного пустого архива. Для `store` стоимость заголовка — 5 байт, а для сжатых методов размер исходных данных кодируется varint.

| Смещение | Размер | Значение |
|---:|---:|---|
| 0 | 1 | код: `F0` store, `F1` LZSS+Huffman, `F2` Huffman, `F3` delta+LZSS+Huffman, `F4` RLE, `F5` repeat, `F6` generic transform+LZSS+Huffman |
| 1 | 1–4 | исходный размер varint (кроме store) |
| далее | 4 | первые 32 бита SHA-256 |
| далее | переменно | метод-зависимые параметры и payload |

Для метода `repeat` после checksum записываются 2 байта длины повторяющегося блока и сам блок. Для метода `RLE` payload состоит из пар «переменная длина серии + байт». Метод `F6` хранит ID обратимого преобразования перед параметрами Huffman. В режиме `store` размер payload определяется длиной архива, поэтому он не хранится отдельно. Версии 1, 2 и 3 также принимаются при распаковке для совместимости со старыми архивами.

Для методов с Huffman параметры содержат размер декодированного промежуточного потока и пары «символ + длина кода» только для реально используемых символов. Перед универсальными методами проверяются RLE и повторяющийся период: в текущем тесте нулевой файл 100 КБ занимает 11 байт, а повторяющийся текст 6800 Б — 21 байт. Для остальных данных исследуются ограниченные фильтры, выбранные по статистике байтового содержимого. Каждый кандидат сравнивается по фактическому размеру, и ухудшающий результат вариант отбрасывается. Распаковка полностью независима от исходного файла. Проверяются метод, размеры, лимит распаковки, таблица кодов, границы LZSS и контрольная сумма. Повреждённый или обрезанный архив возвращает JSON-ошибку, а не приводит к падению процесса.

## Запуск

Требуется Node.js 18+:

```bash
npm start
# открыть http://localhost:3000
npm test
```

Порт можно изменить: `PORT=8080 npm start` (в PowerShell: `$env:PORT=8080; npm start`).

## API

```bash
curl http://localhost:3000/v1/health
curl --data-binary @input.bin -H "Content-Type: application/octet-stream" http://localhost:3000/v1/compress -o archive.sarc
curl --data-binary @archive.sarc -H "Content-Type: application/octet-stream" http://localhost:3000/v1/decompress -o restored.bin
```

Успешные POST-ответы имеют `Content-Type: application/octet-stream`. Ошибки имеют вид `{"error":{"code":"...","message":"..."}}`. CORS разрешён для песочницы и локального пользовательского интерфейса. Запросы читаются потоково по HTTP-чанкам; перед обработкой собираются в ограниченный буфер, чтобы алгоритм мог сравнивать кандидатов. Максимальный исходный файл — 128 МиБ.

## Коэффициент и популярные форматы

Коэффициент считается так: `K = размер исходного файла / размер архива`. Например, `6800 / 60 = 113.3x`. В интерфейсе также показывается размер архива в процентах от исходного. Расширение не используется для выбора метода: архиватор смотрит на байты, поэтому это только практическая ориентировочная карта:

| Категория | Примеры | Обычно |
|---|---|---:|
| Текст и структурированные данные | TXT, JSON, XML, HTML, CSV, JS, CSS, исходный код | 3–20x |
| Несжатые данные | BMP, PPM, RAW, WAV, PCM | 2–10x |
| Смешанные бинарные форматы | PDF, DOC, базы данных, бинарные записи | 1–5x |
| Уже сжатые форматы | PNG, JPEG, MP3, OGG, AAC, ZIP, 7Z | около 1x |
| Случайные байты | криптографические данные, зашифрованные файлы | около 1x |

Это не гарантии: пустой файл, например, имеет специальный архив размером 1 байт, а повторяющийся тестовый текст может дать существенно больше 20x. Для точных результатов на конкретном наборе файлов используйте benchmark:

```bash
node scripts/benchmark.js file.txt data.json image.bmp audio.wav archive.zip
```

Скрипт выводит фактический размер, процент, коэффициент и время для каждого файла.

## Ограничения и развитие

Это надёжная первая версия, а не промышленный архиватор: содержимое целиком находится в памяти, нет многотомных архивов и потоковой распаковки на диск. Следующие улучшения — блочное LZSS для меньшего пикового потребления памяти, более быстрый hash-chain на больших файлах, специальные безопасные фильтры PCM/изображений и интеграционные тесты производительности на фиксированном корпусе. Для PNG/JPEG/MP3/ZIP случайный или уже сжатый payload обычно выбирает `store`; добавление новых методов не меняет старые архивы, так как неизвестный method корректно отклоняется.
